## 〇、最重要的发现——可能推翻`0008_stock_ledger.sql`的一个假设

`0008_stock_ledger.sql`的设计前提是"出库/消耗方向根本没有可靠数据源，只记入库"。**这个前提可能是错的**：

`库管\盘点\7月\附表2：AU6D-20260731 库存盘点表 - 高晨歌.xlsx`的"盘点数据填写"sheet（760行×37列，真实数据非模板）明确有这些列：**物料编码、物料名称、库存数量、盘点数量、总盘点数量、消耗量、消耗量异常原因备注**——`消耗量`是海底捞内部系统自己算出来导出的，不是我们倒推的。`库管\盘点\7月\AU6D门店底料和国内开货物料日均2026.07.26.xlsx`同样有`总库存`/`门店库存`/`大库库存`/`日均使用量`这些列，且物料号（如`3002688`）看起来是海底捞内部系统的物料编码，不是P1的SKU。

`库管\盘点\`目录下4月-7月每月都有一套"AU6D X月成品入库/出库/酱料入库/出库/员工餐领用"PDF，命名规律一致，大概率是同一个内部系统每月固定能导出的报表。

**这跟用户此前说的"其他的我这里没有什么数据"不完全一致**——用户可能是指"没有实时API/流水级别的数据"，但**按月导出的结构化库存快照+消耗量数据其实是有的**，只是分散在这些PDF/xlsx文件里，需要人工每月导出，不是自动同步。这个差异需要用户确认：这些月度导出文件，是否可以作为`stock_ledger`"出库方向"未来数据源的候选（比线A原设想的"完全没有出库数据"乐观得多），要不要据此重新评估`0008`的设计范围。**这条不影响已经commit的4个migration本身是错的——只是说明当初做设计判断时的信息不完整，值得回头看一眼。**

## 三、问题预估（对照P2_清洗与匹配规则.md 15类问题清单，基于抽样，不是逐条核实）

| 问题类型 | 预估情况 |
|---|---|
| 2. 供应商名称格式差异 | **确认存在**：抽样发现至少2处("Coworkc"疑似"Cowrock"、"Four season"疑似"Four Seasons")，29个供应商sheet需要逐个跟P1供应商表核对，估计还有更多 |
| 3. 物料名称与P1主数据不一致 | 日均表用的是海底捞内部系统物料码+品名，不是P1标准物料名称，几乎每一行都需要走匹配流程(60行×至少2个月份版本) |
| 8/9. 一票多单/多票一单 | 未核实，发票校验总表里没有直接的"对应哪次收货"字段，需要靠日期+供应商+金额反推，跟P2_清洗与匹配规则.md第10条"缺少单号需要反推归属"是同一类问题 |
| 10. 缺少单号 | 发票校验总表本身有Invoice No.列，但**只有部分行填了**(216行填了日期，但Invoice No./Amount/GST三列是否都填全未逐行核实，第一批抽样的CFC sheet前3行显示日期有值但金额列是空的——需要专门统计"日期填了但金额没填"这类不完整行有多少) |
| 11. 日期格式异常 | 抽样看到的日期是"1/8/2026"这种文本格式（不是Excel日期类型），中澳DD/MM格式需要专门确认，不能假设 |
| 13. 内部入库误判外部采购 | `盘点/`月度PDF里"员工餐领用"、"酱料入库/出库"这类如果后续要处理，需要明确区分"外部供应商采购入库"vs"店内酱料/半成品内部流转"，不能混着按外部采购处理 |
| 15. 重复导入 | `炒料原料统计表.xlsx`在两个位置各一份、`仅复制-4月发票校验总表.xlsx`文件名本身就暗示可能是副本——这两处需要先用sha256对比是否内容完全相同，相同的话只算一份 |

## 四、风险点

1. **OCR处理约65-70个历史PDF的准确率/成本未知**——`ocrParsingService.js`目前是为实时单据流程设计并测试过的，没有针对历史批量场景做过验证；部分PDF文件很大（14-17MB），是否所有页数都是需要提取的发票内容还是包含无关页面（比如Statement对账单跟发票混在同一个供应商文件夹里），需要先按文件类型分类，不能不分青红皂白全部丢给OCR
2. **海底捞内部系统月度导出格式一致性未知**——`盘点/4月`~`7月`的PDF命名高度一致，暗示是固定模板导出，但只验证了文件名规律，没有逐份核实字段是否真的月月一致（比如7月的`盘点数据填写`sheet有"消耗量异常原因备注"这一列，不确定4-6月的PDF格式版本是否有对应信息，PDF比Excel更难做这种逐列核对）
3. **第〇节提到的"消耗量有数据源"这个发现，直接影响已经commit的`0008_stock_ledger.sql`设计是否需要调整**——这不是本次扫描能替用户决定的事，需要用户看完这份报告后明确一句话：这批月度库存/消耗数据，愿不愿意/方不方便每月手动导出录入系统，如果愿意，`stock_ledger`该不该加一个"月度盘点消耗量回填"的数据来源类型
4. **供应商sheet名到P1供应商ID的映射，没有复用一个现成的自动化脚本**——P1阶段的供应商匹配逻辑是在Excel/Python脚本里跑的（`scripts/lib/`下的相关脚本），这些脚本目前的`SOURCE_DIR`指向`库管`根目录，如果要处理的历史P2文件本身也在`库管`根目录，理论上可以复用，但没有验证过对这批新文件直接可用
