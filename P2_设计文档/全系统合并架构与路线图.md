## 二、现状盘点

### 2.1 已有的两条线

**主线 A(库管根目录,P1/P1b/P2 数据清洗)**:
- P1 物料/供应商/分类主数据:已有正式基线 `P1_物料供应商分类_最终版_20260813_011015.xlsx`(哈希已核实未变),仍有约18项无供应商物料、57组物料合并待人工确认。
- P2 采购/入库/发票/库存流水:已完成 ER 设计和字段字典(见 [[P2_数据库设计.md]]),8张正式表 + 6类待确认表,**但尚未落地任何实际数据**——原计划是等 P1 收尾后"扫描 P2 原始文件"再清洗。

**主线 B(`haidilao-receiving-app`,已实际开发,进度比本文档最初写的时候更靠前)**:
- 前后端功能齐全:飞书 OAuth 登录、按供应商的"今天有没有送货→验收项目勾选→照片上传"流程、总览看板。
- **2026-09-13 发现:项目已经有 `.git` 仓库和 GitHub 远程(`github.com/GCG99/haidilao-receiving-app`),已合并到 v4.3,有 `render.yaml` 部署蓝图**——本文档最初写的时候(当天早些时候)这些都还不存在,是并行开发出来后合并进来的,不是我这次改的。
- **已经有一层 OCR,但要看清楚它实际做了什么**:上传"送货单照片"后,服务端调用**飞书通用文字识别**(整张图转纯文本),再用一份**关键词规则表**(比如文本里出现"牛"就猜这次送货涉及"牛肉"验收项)去**预先勾选验收清单里的复选框**,员工可以手动改回去。这**不是**结构化的品项+数量+单价提取,也没有匹配到 P1 的 SKU,更没有写入任何采购单/入库单(这两张表现在还不存在)。可以理解成:已经验证了"拍照→OCR→自动做点什么"这条链路能跑通,但离 Phase 1 真正要的"SKU+数量+金额结构化录单"还有明显距离,不是"OCR已经做完了"。
- 目前没有独立数据库,仍然直接读写两个飞书 Base。

### 2.2 两条线的落差,决定了合并后第一步要做什么

P2 的 ER 设计(采购单→到货验收→入库单→发票→库存流水)是按"单据都有 SKU 和数量"设计的;而收货小程序目前最多做到"哪个供应商今天送没送货、OCR文字关键词猜一下验收类别、有没有拍照片"。合并不是简单地"把两个 Base 拼一起",而是要把收货小程序升级到能承载 SKU/数量/金额,才能挂到 P2 的 ER 结构上。这是路线图里 Phase 0/1 要解决的问题,不是后面才发现的坑。

## 三、合并后的总体架构

```
                     ┌─────────────────────────┐
                     │   定制网页系统(新)        │
                     │   Express 后端 + 独立DB   │   ← 唯一权威数据源
                     │  (现 haidilao-receiving-  │
                     │   app 的 server/ 扩展而来) │
                     └───────────┬──────────────┘
                                 │ 单向为主(权威→飞书)
                                 │ 少量白名单字段允许反向同步
                     ┌───────────▼──────────────┐
                     │   飞书多维表(降级为副本)   │
                     │  供协作/移动端/通知使用     │
                     └───────────────────────────┘
```

- **数据库**:建议 PostgreSQL(Render 原生支持,和现有部署目标一致;后续做金额汇总、库存流水滚动结余、跨表聚合查询都比飞书原生能力强得多,这也是 [[系统架构与实施计划.md]] 里"定制网页系统"一直想要的能力)。
- **表结构**:直接复用 [[P2_数据库设计.md]] 里已经设计好的 8 张表(采购单主/明细、到货验收、入库单主/明细、发票、附件、库存流水)+ P1 的物料/供应商/分类字典表,不用重新设计 ER。
- **飞书角色**:现有两个 Base(供应商计划表、收货记录表)保留,但角色从"数据来源"变成"从新数据库同步出去的协作视图",供非技术同事在飞书 App 里查看/简单维护。
- **收货小程序的登录/上传/OAuth 代码原样保留**,只是把"读写飞书"换成"读写自己的数据库,数据库再单向同步到飞书"。这部分改造量适中,不是推倒重来。

### 4.1 OCR 录单设计要点(Phase 1 展开)

**现状(2026-09-13 核实过代码,不是猜的)**:`server/index.js` 的 `/api/ocr/delivery-note` 接口调用**飞书通用文字识别**,拿到整张图的纯文本(`text_list`),再用一份写死的关键词规则表(`ocrKeywordRules`,比如文本含"牛"→猜 `beef` 类别为 true)去预先勾选验收清单的复选框。这是"整图转文字+关键词命中"的粗粒度分类,**没有版面/表格结构识别,没有数量,没有单价,没有和 SKU 关联**。

**和现有代码的一个直接协同点**:收货小程序已经要求"今天有送货 → 必须先传送货单照片",这批照片本身很可能就是采购单/入库单的原始凭证(供应商送货单上通常就带品名/数量,有时还有单价)。也就是说 Phase 1 不一定需要给用户新增一个"录单"页面单独拍照——可以复用已经在收的"送货单照片"作为新 OCR 流程的输入源,只是把"识别出来干什么"这一步整个换掉。这一点需要你确认:送货单照片目前的抓拍质量/角度是否够做结构化提取用,还是需要单独引导"拍清楚一点"或加一个专门的"单据"照片位。

**OCR 技术路线,这是个需要你决定的分岔,列出来给你选,不替你定**:
- **多模态大模型直接读图**(比如喂给 Claude 的视觉能力,输出结构化 JSON:品名/数量/单位/单价):优点是对手写体、供应商各种不规范的送货单格式适应性强,不需要提前对接固定模板,而且是从现有"飞书整图转文字"直接可以升级的方向;缺点是逐张调用有 token 成本,量大了要算成本。
- **专用 OCR/发票识别 API**(如阿里云/百度/腾讯的通用文字识别或增值税发票识别接口):对标准格式的正规发票(尤其是澳洲 Tax Invoice 如果有固定模板)识别率和结构化程度可能更高、单价更低,但对手写送货单、非标准供应商单据的适应性通常不如大模型。
- **两者分工**:发票(通常是打印规范单据)走专用发票 OCR,供应商手写/非标送货单走大模型视觉识别——复杂度更高但准确率组合可能最优。
- **继续用飞书 OCR,只是把"关键词猜类别"换成"喂给大模型做结构化解析"**:飞书 OCR 出来的纯文本本身也可以直接喂给大模型去抽取结构化字段,不一定要换掉飞书这一层,只换后面的解析逻辑——如果不想引入新的第三方账号/计费,这是改动最小的路径。

**不管走哪条技术路线,OCR 输出永远先落"录单_待确认"状态,不直接写入正式采购单/入库单表**——这是沿用 P1/P2 已经验证过的"建议≠确认"机制:OCR 识别出的品名要过一次 P1 物料主数据的匹配(复用 [[P2_数据库设计.md]] 里"采购单物料匹配_待确认"的设计),数量/单价识别错误只能靠人工核对时发现并改,系统不能假装 OCR 结果就是事实。现有的"关键词预勾选,员工可手动改回去"这个交互模式(建议值可覆盖,不强制)值得原样延续到新的结构化 OCR 上。

## 六、治理规则(延伸自现有双AI协作协议)

- [[project-kuguan-dual-ai-protocol]] 里"Claude 不得替业务做判断、不得自动commit"的原则,同样适用于本路线图里任何"建议值"字段——尤其是 Phase 7 的 AI 开货建议:AI 生成的建议数量/建议供应商永远是独立字段,人工逐条确认写入正式采购单后才算数,任何时候都不允许 AI 输出直接等同于下单。
- 新数据库的 schema 变更、飞书同步白名单字段的增减,视同"影响正式基线的操作",需要先给你看变更范围,你确认后再执行,不在会话里静默改动已上线的表结构。
- 每进入一个新 Phase 前,重复现有协议的"会话握手"习惯:说明本阶段要读写哪些文件/表、是否涉及业务判断、到哪个确认点为止。
