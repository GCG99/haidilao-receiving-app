# 线A/线B整合规划

> 2026-09-18。背景：库管Excel清洗管道的P2设计(《P2_数据库设计.md》《P2_清洗与匹配规则.md》，下称"线A")和
> haidilao-receiving-app的Postgres后端(供应商/物料/收货/发票/Credit/ERP入库单/三方匹配/OCR，下称"线B")，
> 是两条独立发展、没有真正当成同一个数据模型看待过的线。这份文档是Claude+ChatGPT多轮深度讨论
> (用户明确要求"多思考多质疑")后，把两条线理成一条的结论，供后续实施参考。

---

## 一、核心决定：以线B为唯一正式数据库

线A"以后进飞书多维表、再以后考虑定制网页系统"这条落地路线**作废**。理由：

- 线B已经是真实部署上线的Postgres数据库，不是设计稿
- 线B在关键设计点上比线A原方案更成熟：
  - 发票↔收货/入库单用真正的多对多关联表(`invoice_receiving_links`/`invoice_erp_receipt_links`)，
    不是线A原设计的单值外键(线A那种设计挡不住"一张发票合并覆盖多次送货"这种真实场景)
  - 物料名称匹配用状态机(`supplier_material_mapping`：pending/active/superseded/disputed/discarded)，
    比线A"静态待确认表，人工填一次就完事"更适合"新单据持续进来、匹配规则要不断学习"这种场景
  - 已经有真实可用的OCR解析引擎(Claude vision API)，线A完全没有涉及这块
- 再造一套飞书表，等于把已经跑通的匹配/审计/OCR能力重新做一遍，纯浪费

**线A的价值收窄为**：清洗用户手头的历史Excel数据(8月发票校验总表等)，**目标产出从"飞书多维表"改成"能导入线B这个Postgres的结构化数据"**。线A文档里"物料匹配5级优先级"、"任何非精确匹配不直接写正式表"这套规则依然有效、直接复用，只是最终写入目标换了。

## 二、线B缺的两块，要补

线B目前只记录"货/单已经存在之后"的信息(收货、发票、ERP入库单)，缺两块线A认为必需、且经用户确认真实存在的环节：

### 2.1 叫货记录(简化版，不是完整PO)

**用户确认的真实业务**："全部都是我叫货了才送"——每次供应商送货前，用户都会先报一次数量，不是纯被动按配送周期收货。

但线A原设计的采购单(状态机：草稿/已下单/部分到货/已到货/已入库/已开票/已付款/已关闭)对这家单店过度设计——没有"供应商确认/审批"这种正式环节，报了就等送。

**改用简化版"叫货记录"表**，不建状态机：

| 字段 | 说明 |
|---|---|
| 叫货记录ID | 主键 |
| 叫货日期 | |
| 供应商ID | 关联供应商 |
| 明细 | 物料+叫货数量(子表，一条叫货记录对多个物料) |
| 备注 | |
| 关联收货记录 | 到货后回填，关联到`receiving_records`，用于核对"叫的和到的是否一致"——这是叫货记录存在的主要价值，不是走流程 |

### 2.2 库存流水表——如实承认自己不是"唯一真相"

**用户确认的真实情况**："有一部分物料每周会统计一次(盘点)，其他的我这里没有什么数据，如果后面发现有内部库存流水的，我再添加。"

海底捞内部系统本身可能有权威库存数据，但用户目前拿不到/没对接。所以这张表**不能假装是线A文档说的"全系统库存变化的唯一真相"**——出库/消耗方向根本没有可靠数据源。

设计原则：

1. **入库方向如实记录**：采购/收货/入库单已经有可靠数据源(线B已有)，持续记流水
2. **出库/消耗方向不装**：目前唯一能拿到的是周期性盘点(部分物料，每周)，不是逐笔消耗记录。消耗量只能靠"两次盘点之间的入库量+期初盘点-期末盘点"倒算出一个区间估计，不是真实的逐笔出库流水
3. **"当前库存"这个数字必须标注是估算值**：对有盘点的物料，是"上次盘点数+盘点后的入库量"，UI上要清楚写"估算，基于N天前的盘点"，不能假装是实时准确库存。没有盘点的物料，压根不提供"当前库存"这个数字，避免给假象
4. **表结构留"数据来源"字段**：盘点/入库单/(预留)未来内部系统API——以后真的接上内部系统的库存数据，不用改表结构，加一种来源类型即可

## 三、周盘点"协助填写"——具体功能

用户明确要求："后面还想协助我填写这个每周统计"。按讨论出的优先级(已跟用户对齐)：

1. **到点提醒**：哪些物料这周该盘点了(基于配置好的"每周盘点物料清单")
2. **预设默认值**：填写界面按"上次盘点数+这期间入库量"这个**简单加减法**(不是机器学习预测——问过用户，用户对ML预测感兴趣，但单店规模+每周频率的数据量级现阶段不够训练出有效模型，属于冷启动没数据比简单算法还不准的经典场景，结论是先用简单算法跑几个月攒够真实历史数据，之后再评估要不要升级成ML预测)，预先带出参考值，用户只需要改动跟实际不一样的地方
3. **差异过大提示**：填的数字和预设默认值差太多(比如预计50填了5)，跳出来提示确认一下，防止手滑
4. **(远期可选)语音/拍照转数字**：复用已经在用的Claude vision API技术(跟发票OCR同一套思路)，识别手写盘点表或语音报数——优先级最低，等前3项跑稳了再考虑
